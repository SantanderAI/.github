# Governance — SantanderAI open-source organization

> **Audience.** This document is referenced by every repository in the
> `SantanderAI` GitHub organization (e.g. `gen-fraud-graph`'s `CONTRIBUTING.md`).
> Final destination: `SantanderAI/.github` repository, file `profile/GOVERNANCE.md`
> (or `GOVERNANCE.md` at the root).

## 1. Mission

`SantanderAI` is the public-facing GitHub organization through which Santander
Group releases selected AI/ML research and engineering artifacts as open source.
The mission is to enable external research, contribute back to upstream
ecosystems, and increase the quality of our internal engineering through public
exposure of code we are proud of.

## 2. Roles

| Role | Responsibilities | Scope |
|---|---|---|
| **OSPO Lead** | Org owner, policy enforcement, publication approvals, member onboarding/offboarding, quarterly audits | Org-wide |
| **Security Champion** | Security review of new repos, secret-scanning escalation, vulnerability response coordination | Org-wide |
| **Repo Maintainer** | PR reviews, releases, community engagement, day-to-day issue triage | Per repo |
| **Legal Advisor** | License review, CLA/DCO enforcement, trademark and copyright review | On-demand |

Owners of the `SantanderAI` org must include at least the OSPO Lead and one
deputy (no single point of failure). Every individual repository must have a
named Responsible Maintainer listed in its `CODEOWNERS` file.

## 3. Service-level agreements

| Process | Owner | SLA |
|---|---|---|
| New repository publication review | OSPO + Security | 5 business days |
| External PR — first response | Repo Maintainer | < 1 week |
| Employee offboarding (org removal, PAT/SSH key revocation) | OSPO + HR | Within 24 hours |
| Security incident triage | Security Champion | Per the repo's `SECURITY.md` |
| Quarterly access review | OSPO Lead | Every 90 days |

## 4. Publication decision framework

Before any internal repository is published under `SantanderAI`, the author and
the OSPO must jointly confirm all six gates:

1. **Business value** — clear external benefit and/or strategic rationale.
2. **Competitive risk** — no disclosure of confidential algorithms, models or
   datasets that would harm Santander's competitive position.
3. **Security risk** — no secrets, internal URLs, internal hostnames or PII in
   the source tree or git history; CodeQL and dependency scans clean.
4. **Legal clearance** — license compatible with all dependencies; trademark and
   copyright reviewed; CLA mechanism in place.
5. **12-month maintenance commitment** — a Responsible Maintainer has explicitly
   accepted 12 months of triage and security-fix obligations.
6. **Quality bar** — test coverage >= 90 %, full CI green, README + CONTRIBUTING
   + CODE_OF_CONDUCT + SECURITY + LICENSE present.

The OSPO Readiness Report (`OPENSOURCE_READINESS_REPORT.html`, generated by the
internal `oss-readiness` skill) records the gate evaluation. Publication is
blocked until every gate passes and the OSPO Lead, Security Champion and Legal
Advisor sign off.

## 5. Member lifecycle

### Onboarding

- Each contributor uses an **individual public GitHub account** (not a shared
  account, not the enterprise SSO identity).
- The corporate ID -> GitHub username mapping is recorded in the IAM system so
  attribution can be audited.
- 2FA is **mandatory** for every member; SSO with required 2FA is preferred.
- New members are added to the most-restrictive team that grants the access
  they need.

### Offboarding

When an employee leaves the company:

1. HR notifies the OSPO Lead within one business day of the termination date.
2. The OSPO removes the GitHub user from all org teams within 24 hours.
3. All Personal Access Tokens and SSH keys owned by the departing user are
   revoked.
4. If the departing user was the sole owner of any repository or workflow
   secret, ownership is transferred before removal.
5. The org audit log is reviewed post-offboarding for any anomalous activity.
6. SCIM provisioning is the recommended mechanism for steps 2-3.

## 6. Repository protection (baseline)

Every repository in `SantanderAI` inherits the following protections at
publication time:

- **Branch protection on `main`** — PR required, >= 1 CODEOWNERS approval,
  status checks (lint, tests, SAST, dependency scan, license check, pattern
  check) must pass, conversation resolution required, linear history enforced,
  signed commits required, admin bypass disabled.
- **Tag protection on `v*`** — only Repo Maintainers can create release tags.
- **Push protection** — GitHub native Secret Scanning with Push Protection
  enabled at the org level (blocks the push, not just detects post-hoc).
- **Force-push and branch deletion disabled** on protected branches.

## 7. Programmatic access

- GitHub **Apps** are preferred over Personal Access Tokens.
- Fine-grained PATs are required when an App is not feasible; they must declare
  minimal scopes and an explicit expiration (max 90 days).
- Workflow secrets are stored only as GitHub Actions encrypted secrets — never
  in the source tree.
- A quarterly token inventory audit is performed by the OSPO Lead.

## 8. Decision-making

For changes that affect more than one repository (workflow templates, CLA
text, governance updates), decisions are recorded as PRs against this repository
(`SantanderAI/.github`). Approval requires the OSPO Lead plus one Security
Champion review.

For per-repository decisions (architecture, features, releases), the Repo
Maintainer is the decision authority, with appeal to the OSPO Lead.

## 9. Amendment process

This document is amended by PR with OSPO Lead approval. Material changes
(roles, SLAs, gates) require additional Legal Advisor review and a 7-day
comment window before merge.
